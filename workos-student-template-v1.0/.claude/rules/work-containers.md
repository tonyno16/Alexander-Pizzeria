# Work Containers (Areas & Projects)

Areas and projects share one discipline: a clean root, an `_overview.md` control tower, and durable truth linked from `00-brain/`. This rule covers both. The only place they genuinely differ is the **Area vs Project** section below.

## Area vs Project

- **Area** = ongoing function, no finish line (sales, support, content, ops). Recurring work lives here.
- **Project** = time-bound outcome with a finish line (a launch, migration, campaign, build).
- If both could fit: prefer Project for time-bound outcomes, Area for recurring operations. Promote a project into an area only when the work becomes genuinely ongoing; never let a project become the permanent home for an ongoing function.
- **[Primary area](../../00-brain/glossary.md#primary-area)** = the accountable area for a project. It is the canonical relationship. [Related areas](../../00-brain/glossary.md#related-areas) are context links.

## Behavior (both)

- Read the nearest `_overview.md` before working in the container.
- Treat `_overview.md` as the control tower: purpose/status, decisions, risks, linked work, next action, next decision, artifacts, handoff, archive criteria.
- Keep the root clean — only `_overview.md` lives at the root unless a tool requires otherwise.
- Create subfolders only when files exist or are about to: `notes/`, `research/`, `drafts/`, `assets/`, `data/`, `scripts/`, `apps/`, `final/`.
- Update the overview after meaningful state changes, not just because a turn happened.
- Update relationship metadata when creating, archiving, moving, or reconfiguring work. Do not hand-refresh backlink lists at the end of ordinary turns; use `/work-map` for generated views.
- Put durable company/customer/offer/voice truth in `00-brain/` and link it; put team-facing SOPs in Notion/Google Docs and link them.
- Promote repeated workflows into skills; promote durable tools into the container's `apps/`; promote recurring operations out of a project into `02-areas/`.

## Relationship Metadata

Area `_overview.md` frontmatter should include:

```yaml
container_type: area
area_type: function # function | client | venture
```

Project `_overview.md` frontmatter should include:

```yaml
container_type: project
primary_area: 02-areas/<area>/_overview.md
related_areas: []
```

Project metadata is canonical. Area backlink sections are convenience views and
may be generated by `/work-map`.

## Update The Overview When

- Purpose, scope, owner, status, `claude_role`, outcome, success criteria, or timeline changes.
- A decision is made, a blocker is found, or a recurring workflow/tool/source/metric becomes durable.
- A meaningful artifact is created, moved, linked, or finalized.
- A related project/app/area link changes, or a handoff is needed for another thread or teammate.
- A project gains, loses, or changes `primary_area`.
- A next action, next decision, risk, constraint, or archive condition changes.

## Ask Before

- Changing a public promise, strategy, launch timing, budget, owner, or customer-facing commitment.
- Archiving active strategic work when there is real ambiguity.
- Moving work across container boundaries when ownership is unclear.

## Do Not

- Create a new area for a one-off launch/campaign/migration/build, or let a project become the permanent home for an ongoing function.
- Create `projects/`, `03-projects/`, or nested PARA folders inside an area by default.
- Dump drafts, assets, exports, or data into the container root.
- Copy evergreen brain facts or whole external docs locally — link canonical sources.
- Hide important decisions in drafts or chat instead of `_overview.md`.
- Create empty folder theater.

## Verification

- Root stays clean; `_overview.md` is current enough for a new thread to start cold.
- Outcome/success criteria clear (projects); active projects have `primary_area` or an explicit `none` reason.
- Durable facts have one canonical home; artifacts are in purpose folders.
- Handoff and archive criteria are current.
